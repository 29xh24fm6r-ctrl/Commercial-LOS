## Were Generated Services / Data Sources Added?

No. `src/generated/services/`, `.power/schemas/appschemas/dataSourcesInfo.ts`,
and `power.config.json` database references are TOOLCHAIN-auto-generated
("Do not modify it manually. Changes to this file may be overwritten." /
"autogenerated. Do not edit this file directly."). Registering
`cr664_dealstagereferences` / `cr664_dealstatusreferences` requires the
PAC / Power Apps data-source generator + a redeploy so the deployed app
binds the data source. Hand-editing those files would create a
registered-but-unusable data source at runtime and violate the
generated-file discipline. That registration is therefore a separate
operator/toolchain step, intentionally NOT done in this code phase.

## Was A Resolver Added?

Yes -- `src/deals/newDealReferenceResolver.ts`, a pure, fail-closed
resolver foundation:

- It performs NO IO itself; it reads rows through an INJECTED
  `NewDealReferenceReader`. No reader is wired in app runtime yet
  (data sources unregistered), so app callers get `notConfigured` and
  + New Deal stays disabled.
- Typed result union: `ready | notConfigured | missingStage |
  missingStatus | duplicateStage | duplicateStatus | inactiveStage |
  inactiveStatus | serviceError`.
- Input selects a target by stable `code` (preferred) or `name`, never a
  GUID; the resolver never invents a default (no code/name -> missing).
- Fail-closed: missing row, none-active (inactive), more-than-one-active
  (duplicate), reader throw (serviceError), and absent reader
  (notConfigured) all return a non-ready result.
- It emits an `@odata.bind` path ONLY in the `ready` case, built from a
  verified unique active row id:
  - `cr664_StageReference@odata.bind: /cr664_dealstagereferences(<id>)`
  - `cr664_StatusReference@odata.bind: /cr664_dealstatusreferences(<id>)`
- A `ready` result does NOT enable + New Deal; wiring a governed audited
  create is a separate, later phase.

## Was Read-Only Value Inspection Added?

Yes -- a new operator script mode `--inspect-stage-status-values`
(`runInspectStageStatusValues` in `scripts/phase122-lookup-repair.mjs`).
It is pure GET on `cr664_dealstagereferences` and
`cr664_dealstatusreferences` (selecting only
`<primaryId>,cr664_name,cr664_code,cr664_activeflag`), prints each row's
active/inactive state, and flags duplicate code/name and zero-active
risks so an operator can confirm a unique active default exists. It
issues no POST/PATCH/DELETE, no PublishXml, and no bypass/suppress/force
headers, and it is mutexed with every other script mode.

```
node scripts/phase122-lookup-repair.mjs --inspect-stage-status-values
```

## Do Actual Reference Rows Exist?

Not inspected live in this phase (no operator commit/auth run was
performed here). The `--inspect-stage-status-values` mode is provided so
the operator can confirm row presence, uniqueness, and active state
before any future resolver wiring. Until that confirmation, the resolver
correctly returns `notConfigured` in app runtime.

## Why + New Deal Remains Disabled

- The Stage/Status data sources are not registered, so no live reader can
  be constructed; the resolver returns `notConfigured`.
- Even with a reader, a `ready` result is foundation-only and is not
  wired to any create path.
- `NOT_WIRED` still carries `new-deal-create`; the Admin New Deal panel
  still renders a disabled "Create deal" placeholder.

## Exact Next Steps To A Controlled Create

   the two resolved binds, a `cr664_AuditEvent`, typed outcome, and
